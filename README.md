# TingiProof *(working title; not final)*

> **Status: Early idea only — nothing is finalized.** This README is a discussion draft for one possible hackathon direction. The team has not committed to this concept or begun implementation. The project name, target users, problem statement, proposed features, technology choices, and even the overall idea may change substantially—or be dropped entirely—after team discussion, research, and feedback. There is no working prototype.

## What we're considering

One possible direction is a lightweight tool to help independent sari-sari stores and neighborhood retailers document delivery discrepancies with wholesalers or distributors.

For example, an order and its delivery might differ because of missing items, damaged goods, or substitutions. We're interested in learning whether retailers experience this often, how they currently handle it, and whether the process creates enough difficulty to justify a dedicated tool.

**This is only a problem hypothesis.** We have not yet confirmed how common the problem is or whether existing tools already handle it adequately.

## Possible target users

Owners or staff of independent sari-sari stores and small neighborhood retailers in the Philippines who receive deliveries from wholesalers or distributors.

This audience is tentative and may be narrowed or changed after we speak with potential users.

## One possible solution direction

If research supports the problem, a prototype could explore a simple workflow for recording a delivery discrepancy and following up on it. Possible functions might include:

- **Expected-versus-received checklist:** Compare ordered quantities with the quantities received.
- **Discrepancy notes:** Record missing, damaged, or substituted items.
- **Evidence attachments:** Add relevant photos or documents when useful.
- **Claim status:** Record whether an issue has been reported, acknowledged, or resolved.
- **Resolution history:** Note outcomes such as replacement, credit, refund, or explanation.
- **Outstanding-issues summary:** Review unresolved discrepancies and their recorded value.

These are examples for discussion, **not a final feature list**. The eventual solution could be much smaller, different, or unrelated if research points in another direction.

## Questions to investigate

Before choosing this as the hackathon project, we need to find out:

- How often do delivery discrepancies happen for the potential target users?
- How do retailers record and resolve these issues today?
- What evidence or information do suppliers need when reviewing a claim?
- Do existing point-of-sale, ordering, or supplier tools already solve this well?
- Would a separate tool provide enough value for retailers to use it?
- Is this problem significant and feasible enough to address with a three-day prototype?

## If the idea moves forward

A small prototype could test one example workflow using sample data:

1. Enter an example order and its expected quantities.
2. Record what was actually received.
3. Flag a missing, damaged, or substituted item.
4. Create a discrepancy record.
5. Update its status as it is followed up.
6. Review the recorded outcome.

This is an illustrative test scenario only. It is not a committed development plan, and the final scope would depend on research, team decisions, and hackathon time.

## Possible evaluation criteria

If we build and test a prototype, we could evaluate:

- Time needed to document a discrepancy.
- Completeness of the recorded details and supporting evidence.
- Time needed to find the status of an unresolved issue.
- Whether target users find the workflow useful compared with their current process.

We will not claim that the concept reduces losses or improves resolution rates unless testing produces evidence supporting those claims.

## Technology

**No technology stack has been selected.** If the team chooses to proceed, a mobile-friendly web app and simple data storage may be one feasible approach. Hardware and AI are not assumed to be necessary for this initial idea.
